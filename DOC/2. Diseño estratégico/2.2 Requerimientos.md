# 2.2 Requerimientos

Requerimientos funcionales (RF) y no funcionales (RNF) de Llavero, derivados de las decisiones ya tomadas en la estrategia de migración (`estrategia-migracion/`) y la matriz de roles (`roles-y-vistas.md`).

## Requerimientos funcionales

### Autenticación y roles

| ID | Requerimiento |
|---|---|
| RF01 | El sistema debe permitir el inicio de sesión exclusivamente vía **Office 365** (Microsoft Entra ID), sin login local de usuario/contraseña, para los tres roles del sistema. |
| RF02 | El sistema debe reconocer tres roles: **Administrador**, **Auxiliar** y **Portero**, cada uno con una ubicación asignada (oficina principal, portería superior, portería inferior). |
| RF03 | Los usuarios deben ser precreados por un Administrador (con rol y ubicación asignados); el primer ingreso por Office 365 solo vincula la cuenta por correo institucional, no crea usuarios nuevos automáticamente. |

### Llaves

| ID | Requerimiento |
|---|---|
| RF04 | El sistema debe resolver automáticamente si una lectura de credencial corresponde a una **entrega** o una **devolución** de llave, sin que el usuario deba indicarlo manualmente. |
| RF05 | El sistema debe permitir registrar una entrega de llave de forma manual (sin lectura de credencial) como alternativa. |
| RF06 | Administrador, Auxiliar y Portero deben poder entregar y recibir llaves, sin restricción por su ubicación asignada. |
| RF07 | Al devolver una llave, el sistema debe permitir adjuntar opcionalmente una **novedad** (daño, pérdida, otro). |
| RF08 | El sistema debe mostrar, para cada préstamo de llave activo, un indicador visual del porcentaje de tiempo transcurrido antes de entrar en mora. |
| RF09 | La ubicación de cada entrega o devolución debe derivarse automáticamente del usuario autenticado — **no debe ser un campo seleccionable** en ningún formulario. |

### Préstamos de equipos

| ID | Requerimiento |
|---|---|
| RF10 | El sistema debe permitir registrar el préstamo de uno o varios equipos a la vez (carrito), mediante escaneo de código de barras. |
| RF11 | El sistema debe permitir devoluciones **parciales**: se puede devolver un subconjunto de los equipos de un préstamo, quedando el resto activo. |
| RF12 | Solo Administrador y Auxiliar pueden **entregar** (prestar) equipos. Portero solo puede **recibir/devolver** equipos, no prestarlos. |
| RF13 | Al devolver un equipo, el sistema debe permitir adjuntar opcionalmente una novedad. |

### Disponibilidad y reservas de salones

| ID | Requerimiento |
|---|---|
| RF14 | El sistema debe mostrar una vista de **disponibilidad de salón** que superponga, en un solo calendario, la programación académica oficial, las reservas semestrales y las reservas individuales. |
| RF15 | El sistema debe validar conflictos de horario cruzando las tres fuentes (programación, semestrales, individuales) con la misma lógica, sin importar desde cuál de los tres flujos se esté creando la reserva. |
| RF16 | El sistema debe permitir cargar la programación académica oficial por archivo Excel institucional (solo Administrador). |
| RF17 | El sistema debe permitir crear reservas semestrales (franjas recurrentes semanales) por grupo, y cancelarlas solo si fueron creadas manualmente (no si vinieron de carga institucional). |
| RF18 | El sistema debe permitir crear reservas individuales (de fecha específica), quedando aprobadas automáticamente al crearse — no hay paso de aprobación manual. Administrador y Auxiliar pueden gestionar reservas individuales y semestrales al mismo nivel. |

### Monitores (delegación)

| ID | Requerimiento |
|---|---|
| RF19 | El sistema debe permitir a un Administrador o Auxiliar delegar en un estudiante u otra persona el permiso de reclamar/entregar la llave de un docente en su nombre. |
| RF20 | Portero no debe tener acceso a la gestión de delegaciones (Monitores). |

### Novedades y notificaciones

| ID | Requerimiento |
|---|---|
| RF21 | El sistema debe permitir registrar novedades (daños, pérdidas, observaciones) asociadas a una llave o un equipo. |
| RF22 | Auxiliar debe poder ver y cerrar una novedad (cambiar su estado de abierta a cerrada); solo Administrador puede definir la solución de una novedad. |
| RF23 | El sistema debe enviar automáticamente recordatorios de devolución y avisos de mora escalonados, según los umbrales configurados. |
| RF24 | Administrador y Auxiliar deben poder enviar notificaciones manuales y reenviar notificaciones fallidas, con el mismo nivel de acceso entre ambos. |

### Comunidad (docentes, estudiantes, empleados)

| ID | Requerimiento |
|---|---|
| RF25 | Los datos de la comunidad universitaria (docentes, estudiantes, empleados) deben sincronizarse automáticamente desde el sistema institucional, sin edición manual dentro de Llavero. |
| RF26 | Administrador y Auxiliar deben poder consultar el directorio de comunidad, incluyendo datos de contacto (correo y teléfono). Portero no tiene acceso a este directorio — identifica personas exclusivamente por lectura de credencial. |

### Historial

| ID | Requerimiento |
|---|---|
| RF27 | El sistema debe mantener un historial de todas las entregas y devoluciones (llaves y equipos), indicando quién las procesó. |
| RF28 | Portero debe ver únicamente el historial de lo que él mismo procesó; Administrador y Auxiliar ven el historial completo, incluido lo procesado por cada Portero. |

## Requerimientos no funcionales

| ID | Requerimiento |
|---|---|
| RNF01 | El backend debe implementarse como un **monolito modular**, con cada módulo dividido en 5 capas fijas (`model`, `repository`, `domain`, `service`, `controller`), donde ningún módulo accede directamente al modelo o repositorio de otro. |
| RNF02 | Las operaciones de entrega y devolución de llaves y equipos deben ejecutarse dentro de **transacciones atómicas** de base de datos, para evitar condiciones de carrera (doble préstamo concurrente del mismo recurso). |
| RNF03 | El endpoint de sincronización de datos de Comunidad debe estar protegido por API key. |
| RNF04 | La sesión de la API debe manejarse con JWT de acceso y refresco, con rotación de un solo uso y detección de reuso del token de refresco. |
| RNF05 | El sistema no debe depender de comunicación en tiempo real (WebSockets) para su operación — toda interacción se resuelve por solicitud/respuesta HTTP estándar. |
| RNF06 | El sistema debe operar sin necesidad de migrar datos históricos — el despliegue inicial parte de una base de datos limpia. |
| RNF07 | La interfaz debe construirse sobre una librería de componentes consistente (PrimeNG), evitando estilos y comportamientos distintos entre pantallas. |
| RNF08 | La lógica de negocio pura (cálculo de mora, resolución de entrega/devolución, validación de disponibilidad) debe ser testeable sin depender de la base de datos, siguiendo TDD desde el primer módulo construido. |
| RNF09 | El campo de captura de credencial debe validar formato (numérico, hasta 15 dígitos) antes de procesar una lectura, para descartar entradas inválidas o tecleo accidental. |
